# Frontend localization

The frontend supports `en` and `vi`. The backend PR #31 defines `en` as the
default and accepts regional values by reducing them to a supported language.
The frontend therefore defaults invalid or missing preferences to `en`.

Messages use `next-intl` with domain-scoped catalogues under `messages/{locale}`:
`common`, `auth`, `customer`, `provider`, and `administration`. Keys describe
meaning (`administration.authorization.roles.title`), not component position.
User-created role names, permission codes, UUIDs, and request IDs are never
translated.

The preference is stored in the `nexus.locale` cookie (with a localStorage
mirror for client fallback). The root layout reads the cookie so `<html
lang>` and the first server render agree. The shared API transport sends the
backend's actual locale header, `x-lang`, on every client request. This is not
`Accept-Language` in PR #31.

Backend business errors remain authoritative. `ApiError.errorCode` drives
known frontend UX; the backend's localized `message` is the fallback for
unknown codes, and `request_id`/details remain available for diagnostics.

To add copy, add the same semantic key to both locale catalogues, then use
`useTranslations('domain')`. Keep API values and business comparisons in
their raw enum/code form and localize only presentation.
